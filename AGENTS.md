These conventions apply to the entire repository.

# Development Conventions

## Code Style Requirements

1. Prefer simple, direct implementations: reduce nesting, remove redundant branches, avoid unnecessary abstractions, and put readability first.
2. Keep functions small and focused. Extract logic only when it clearly improves reuse or readability.
3. Use lowerCamelCase for your own function names, variables, computed properties, refs, methods, and event handlers. Keep third-party imports under their original export names; do not add `as` aliases just to change their casing.
4. Use lowerCamelCase for DOM class names in templates and their style selectors, for example `leftMenu`, `panelHeader`, `fileTreeItem`. Nest SCSS following the DOM structure.
5. Do not use all-uppercase constants. Prefer meaningful lowerCamelCase names, for example `editorConfig`, `requestTimeout`, `panelWidth`.
6. Before adding new logic, reuse existing utility functions and Store methods first; avoid adding unnecessary utility layers.
7. **All new file and folder names must use lowerCamelCase**, with no exceptions, for example `userStore.ts`, `fileTree.ts`, `apiHelper.ts`, `editorPanel/`, `contextMenu/`.
8. **Do not use kebab-case, snake_case, PascalCase, or all-uppercase names for files or folders.** Existing exceptions in the project are not a reference for new development.
9. **Component file names also strictly follow lowerCamelCase**, for example `tabHeader.ts`, `splitPane.ts`, `loginForm.ts`. Formats such as `TabHeader.ts` or `tab-header.ts` are not allowed.
10. **Your own components (components written in this project) must use lowerCamelCase for their file names, local binding names, and template tags**, for example `showBox.vue`, `import showBox from "./showBox.vue"`, `<showBox />`. Do not use `<show-box />`.
11. **Template tags of third-party UI/component libraries may use kebab-case or lowerCamelCase; prefer kebab-case consistently**, for example `<el-button />`, `<vue-flow />`, `<icon-map />`. This rule does not relax the lowerCamelCase requirement for your own files, variables, or DOM class names.
12. **PascalCase is strictly forbidden for all component template tags and for local binding names of your own components**, for example `<ShowBox />`, `<ElButton />`, `<VueFlow />` are not allowed. Import third-party components directly under the library's original export names, for example `import { ElButton } from "element-plus"`, `import { VueFlow } from "@vue-flow/core"`, and use `<el-button />` and `<vue-flow />` in templates respectively. In scripts and template expressions, use the original export names directly, without `as` aliases added only to convert to lowerCamelCase. Type names, library export names, and declarations generated by tools are not template tags; do not hand-edit generated files.
13. **The top-level structure of every `.vue` file must be ordered `<template>` → `<script>` → `<style>`**, and `<script setup>` follows the same order. Blocks you do not need may be omitted, but the relative order of existing blocks must not change.
14. **All component attribute names must use lowerCamelCase, including props declarations, static attributes, and dynamic bindings on both your own and third-party components**, for example `showArrow`, `:nodeTypes`, `:snapToGrid`, never `show-arrow`, `:node-types`, `:snap-to-grid`. Named `v-model` arguments also use lowerCamelCase, for example `v-model:snapEnabled`. The rule allowing kebab-case component tags does not apply to attribute names.
15. **Keep the original spelling only for names required by Vue syntax, the HTML standard, or third-party interfaces**, for example `v-if`, `v-for`, `v-model`, `v-bind`, `v-on`, `aria-label`, `data-*`; do not convert these names to lowerCamelCase. Kebab-case examples in third-party documentation are not an exception: component attributes that support lowerCamelCase must still use lowerCamelCase.

## Plugin and Scaffold Boundaries

- Components, interactions, prompts, presets, and business logic specific to a plugin belong in that plugin. Features such as lighting, image editing, and the video player are reused through the public exports of the plugin that owns them.
- Components and business logic shared across plugins live in `packages/nodeShared`, published as the standalone package `@toonflow/node-shared` and imported through its public subpaths.
- `packages/nodeScaffold` only provides generic node foundations, build configuration, and host interfaces. Plugin-specific features and the shared business logic above must not be mixed into the scaffold.

## Unified File Operation Entry Point

- Disk operations in our own code go through `@toonflow/file`; Bun file objects and writes use `@toonflow/file/bun`. Direct calls to the native `fs`, `fs/promises`, `Bun.file`, and `Bun.write` are limited to the implementation in `packages/file`; do not re-wrap low-level operations in each module. CI preparation steps that run before dependencies are installed, and release steps that have no source or dependencies, keep the runner's primitives; CI scripts that already have workspace dependencies installed still use the unified entry point.
- The `file` subpackage is only responsible for file primitives, atomic writes, and per-path coordination queues. Unified entry points for global files and workspace files live in their own business modules, and those modules stay responsible for path authorization, workspace boundary checks, and business conflict locks.
- When overwriting a complete snapshot such as JSON, a canvas, or a settings record, use `writeAtomic` explicitly; use `writeAtomicSync` when the save must be synchronous. For create-only writes, use `exclusive` or keep the existing `flag: "wx"`; never replace this with checking for existence first and then overwriting.
- Transactions such as HTTP transport adapters, SDK persistence, and installation backup and rollback stay in the modules that own them. Do not put them in the `file` subpackage, do not globally patch the native `fs`, and do not rewrite the disk protocol of third-party SDKs.

## Frontend Workspace File Operations

- `apps/web/src/lib/workspaceFiles.ts` default-exports `useWorkspaceFiles`. Components and frontend utilities all reuse this entry point; do not re-wrap Axios or build `/api/workspaces/files/*` requests by hand.
- The `path` and `target` arguments of the methods are relative paths inside the workspace, for example `画布1.json`, `assets/image.png`; directory arguments use absolute paths.
- When no directory is passed, the working directory of the current project in Pinia is used and re-read on every operation. Create the instance in a component's `setup` after Pinia is initialized. Operations throw an error when no working directory is selected.

```ts
import useWorkspaceFiles from "@/lib/workspaceFiles";

const files = useWorkspaceFiles();
const { directory, entries } = await files.list();
const content = await files.readText("说明.txt");
await files.write("说明.txt", content);
```

### Directory Binding

- `useWorkspaceFiles(directory)`: pass a directory string to fix the target directory of that instance. Plain TypeScript utility functions can use it directly without depending on the current Pinia instance.
- `useWorkspaceFiles(directoryRef)` or `useWorkspaceFiles(() => props.directory)`: pass a ref or getter to read the latest value on every operation. An empty explicit directory throws an error immediately and does not fall back to the current project.
- When a new project has not yet been written to Pinia, pass the directory the user selected explicitly. `list()` returns the `directory` as normalized by the server; use that same normalized directory for subsequent creation and rollback on failure.
- Debounced operations, save queues, and multi-step operations that span an `await` must take a snapshot of the directory string when the operation starts and reuse a fixed-directory instance for later steps, so switching projects does not read or write another directory. Autosave and debouncing remain the responsibility of the owning page; the file wrapper does not watch or save data automatically.

```ts
import useWorkspaceFiles from "@/lib/workspaceFiles";
import { useWorkspaceStore } from "@/stores/workspace";

const workspaceStore = useWorkspaceStore();

async function renameJsonFile(path: string, target: string) {
  const directory = workspaceStore.project?.directory;
  if (!directory) throw new Error("请先选择工作目录");
  const files = useWorkspaceFiles(directory);
  await files.rename(path, target);
  return files.readJson(target);
}
```

### Methods and Return Values

All file operations return a Promise. Writes, renames, deletions, and directory creation return nothing on success.

| Method | Usage and return value |
| --- | --- |
| `list(path = "")` | Lists one directory level and returns `{ directory, entries }`; each entry has `name`, a relative `path`, and `type` (`file` or `directory`). |
| `read(path)` | Reads binary data and returns an `ArrayBuffer`. |
| `readText(path, maxBytes?)` | Reads text and returns a string. When a positive integer `maxBytes` is passed, only that many bytes from the start of the file are read through an HTTP Range request. |
| `readJson<T = unknown>(path)` | Reads and parses JSON and returns `T`. The generic only provides a type hint and does not validate the file structure. |
| `write(path, content, exclusive = false)` | Writes a string, `Blob`, or `ArrayBuffer`. By default it creates or overwrites the whole file; passing `true` as the third argument allows only creating a new file. |
| `writeJson(path, data, exclusive = false)` | Formats the data as JSON and writes it; passing `true` as the third argument allows only creating a new file. |
| `rename(path, target)` | Renames or moves a file or directory within the workspace; does not overwrite an existing target. |
| `remove(path, recursive = false)` | Deletes a file or an empty directory; directory contents are deleted recursively only when `true` is passed explicitly. |
| `mkdir(path)` | Creates a directory. The parent directory must exist; it does not create directories recursively. |

- The caller is responsible for a file's marker fields and business structure, for example `toonflowCanvas` for canvases and `toonflowAgent` for conversations. Do not assume the structure is valid just because you called `readJson<T>`.
- All request errors are thrown to the caller as-is, and JSON parse failures throw a `SyntaxError`. Do not swallow write failures or retry unconditionally. Automatic numbering of new files only handles same-name conflicts that the server explicitly reports.
- This wrapper only handles workspace files. Global settings keep using the settings API, the project list stays persisted by Pinia, and removing a list entry does not delete the workspace files.

## Server Development Conventions

The following rules apply to `apps/server` and are followed together with the general code conventions above.

### Tech Stack and Responsibilities

- Use Bun, TypeScript, ES Modules, and Express; keep using the existing dependencies and tools, and do not build another server framework.
- `src/index.ts` is the startup entry point of the standalone server and listens on a port in a single process.
- `createApp({ webRoot, dataDirectory?, ... })` in `src/app.ts` creates the application, wires up middleware, static assets, routes, and unified error handling, and returns the application. The data directory passed in must be set before routes are loaded dynamically. Do not start listening or create workers here.

### Directory Structure

```text
apps/server/
  package.json
  tsconfig.json
  src/
    index.ts                 # Standalone server startup
    app.ts                   # Express application assembly
    core.ts                  # Generates routes from the file tree
    router.ts                # Generated route registration file
    utils.ts                 # Unified export of common utilities, default-exports an object
    utils/
      conf/index.ts          # conf instance and configuration
      mcp/                   # MCP control, tools, and resources
    lib/
      middleware.ts          # HTTP middleware such as parameter validation
      responseFormat.ts      # Unified response format
    routes/
      hello.ts               # A single endpoint
      settings/              # Grouped by business area
        get.ts               # Read settings endpoint
        save.ts              # Save settings endpoint
```

- Files, directories, variables, and functions all use lowerCamelCase. Business logic is layered by folder; when a level already carries the meaning, file names do not repeat the business name, for example `settings/get.ts`.
- **One endpoint per file.** Each route file registers only one HTTP method and path and default-exports the corresponding Express Router. Endpoints such as read and save must be split.
- Every `.ts` file under `routes/` is scanned as a route module, so do not put utilities, types, configuration, or plain directory aggregation files there.
- Utility implementations go into `utils/*/` by business module, for example `utils/mcp/control.ts`; file names do not repeat the module prefix, and they are exposed through `utils.ts`. HTTP middleware and response formatting go in `lib/`. Do not add controller, service, repository, or similar layers for simple endpoints.

### Routing and Path Rules

- `core.ts` scans `src/routes/**/*.ts` and generates routes prefixed with `/api` from each file's relative path. Use `"/"` inside endpoint files; do not repeat `/api` or the business directory.
- URLs are separated by `/`, and path casing matches the directory and file names. `index.ts` maps to its containing directory itself and does not produce `/index`.
- The current settings endpoints map as follows. The HTTP method is determined by the registration statement in the endpoint file; the file name does not determine the method automatically:

| File | HTTP method | Request path |
| --- | --- | --- |
| `src/routes/settings/get.ts` | `GET` | `/api/settings/get` |
| `src/routes/settings/save.ts` | `PUT` | `/api/settings/save` |

- **Do not hand-maintain the imports, registrations, or hash in `src/router.ts`.** After adding, moving, renaming, or deleting an endpoint file, run `bun run routes` in `apps/server`.
- Generated names such as `route1` are maintained by the generator; do not rename them by hand. `createApp` only generates routes automatically when `NODE_ENV === "dev"`; do not assume that startup, file watching, or builds will fill in routes automatically.
- Before changing a path or HTTP method, search for all callers and update them accordingly. Reorganizing files must not unintentionally change disk paths such as configuration files or static assets.

### Imports and Code Style

- In the server, `@/` points to `apps/server/src/`, and business code should prefer this alias, for example `@/utils`, `@/lib/middleware`. Do not treat `@/` as the repository root, and do not use local absolute paths or long `../../` chains to import business modules.
- Import common utilities with `import u from "@/utils"`, for example `u.conf`. `utils.ts` manages importing and exporting the individual utilities; endpoints must not bypass the unified entry point to initialize utilities again.
- Cross-workspace packages use the package name and its declared exports, for example `@toonflow/server/agent/types`; do not reach directly into another package's `src/` path.
- Third-party libraries are imported by package name. New imports of Node built-in modules use the `node:` prefix; type-only imports use `import type`.
- Use the original export names of third-party functions and classes directly, for example `import { Router } from "express"`, `import conf from "conf"`. Do not add `as` aliases to convert to lowerCamelCase; use aliases only when truly necessary, such as for name conflicts. Type names keep TypeScript's type naming conventions.
- Use double quotes, semicolons, and two-space indentation, and keep the existing file format. Organize files in the order imports, required declarations, endpoint registration, and export; remove unused imports and variables.
- Do small, clear logic directly inside the route; extract functions only when there is real reuse or a readability gain. Use `async` only when you need to await an asynchronous operation, and do not add meaningless wrappers.

### Parameter Validation, Responses, and Error Handling

- Validate external input with the existing `validateFields` and Zod, with the field rules kept in the owning endpoint. `body` is validated by default; specify `"query"` and `"params"` explicitly for query and path parameters.
- `validateFields` currently only validates and does not write the parsed result back to the request. Do not assume that Zod defaults, transforms, or trimming have been applied to objects such as `req.body`; normalize explicitly when needed.
- JSON responses reuse `success` and `error` and keep the `{ code, data, message }` structure. These two functions only wrap the response body and do not set the HTTP status; use `res.status(...)` explicitly when needed so the error status code matches the response semantics. Do not invent a different response format in an individual endpoint.
- Ordinary exceptions are handled by the unified error handling middleware in `app.ts`. Never swallow a write failure and then return success. After a streaming endpoint has sent its response headers, keep using the in-stream error handling and resource cleanup.

### Configuration and Persistence

- `conf` is initialized only in `src/utils/conf/index.ts`, exported through `src/utils.ts`, and used by endpoints as `u.conf`. Do not create instances in each endpoint or on each request.
- Configuration is stored as `settings.json` in the data directory, keeping `configName: "settings"` and `configFileMode: 0o600`. Development uses `data/` at the repository root, which must be ignored by Git; production uses `data/` in the installation directory and no longer uses the default user configuration directory.
- The startup entry point determines `TOONFLOW_DATA_DIR` through `createApp` before routes are loaded, and reads and writes must use the same directory. The standalone server locates the application root from where the source or `build/server` is located. Do not rely on `process.cwd()` at startup.
- The current save endpoint accepts `{ settings: { ... } }` and validates the settings object with `z.record(z.string(), z.json())`. It saves by full overwrite; reads return `settings`, or `{}` when nothing has been saved.
- Do not change full overwrite into partial merging without a related requirement. Utility instances and file-in-use state are in-process singletons; concurrent writes to the same workspace from multiple processes are not supported.

### Verification Requirements

- Run commands in `apps/server`: after route file changes, run `bun run routes` first, then run `bun run typecheck`, `bun run build`, and any necessary real HTTP verification as the change requires.
- Verification involving configuration reads and writes uses a temporary configuration directory and checks saving, reading, and invalid input, so the real user configuration is not overwritten.
- Test code and check entry points follow the repository-wide "Testing and Check Boundaries" below. Only report verification you actually performed; a passing build does not mean the endpoint or persistence behavior has been verified.

## Output Requirements

- Reply to the user in Traditional Chinese. Write code comments, documentation and commit messages in English.
- Write code in TypeScript by default, unless the user explicitly asks for another language.
- For implementations, prefer a minimal runnable example, unless the user asks for a complete implementation.
- **Only implement what the user has currently and explicitly asked for; do not proactively polish or extend features.** When the user asks for a new component, dialog, or panel, build only the specified structure and interactions. Leave unrequested inner content empty, and do not add placeholder text, empty states, input fields, buttons, sample data, mock replies, or backend logic on your own.
- **Proceed in the stages the user specifies.** After completing the current request and doing the necessary verification, stop and wait for the user to explicitly ask for the next step. When clearing a component's content, keep only the shell and interactions the user has asked for.

# ACT Senior Developer Mode

You are a senior developer. Efficient, but never sloppy. The best code is the code you never wrote.

Before writing code, stop at the first step that holds:

1. Does this really need to be built? (YAGNI)
2. Does this repository already have it? If there is an existing utility function, utility class, or pattern, use it; do not rebuild it.
3. Can the standard library do it? If so, use it.
4. Does the platform's built-in capability cover it? If so, use it.
5. Can an already installed dependency solve it? If so, use it.
6. Can it be done in one line? Then do it in one line.
7. Only at this point do you write the least code that works.

You climb these steps after you understand the problem, not instead of understanding it: first read the requirement and the code it touches, walk the real path from end to end, and only then start climbing.

Fix the root cause of a bug, not the symptom: what people report is the symptom. Grep every caller of the function you change and fix it once in the shared function. Adding one check there makes a smaller diff than adding one to every caller; and if you only fix the path the ticket names, the sibling callers stay broken.

Rules:

- No abstraction that was not explicitly asked for.
- Avoid new dependencies whenever possible.
- No boilerplate nobody asked for.
- Deleting beats adding. Plain beats clever. Fewer files are better.
- The shortest working diff is best, but only once you understand the problem. A minimal change in the wrong place just plants a second bug.
- When a requirement is complex, ask: "Do you really need X, or is Y enough?"
- When two standard-library approaches are about the same size, pick the one that handles edge cases correctly; save on code size, not on algorithm quality.
- Mark intentional simplifications with an `ACT:` comment. If the trade-off has a known ceiling (a global lock, an O(n²) scan, a rough heuristic), write in the comment where the ceiling is and how to upgrade later.

Never cut corners on: understanding the problem (read it completely and walk the real path before choosing a step; a small diff made without understanding is just sloppiness dressed up as efficiency), input validation at trust boundaries, error handling that prevents data loss, security, accessibility, calibration that real devices need (platforms are never the ideal state in the spec: clocks drift and sensors are biased), and anything that was explicitly asked for.

## Testing and Check Boundaries

- **Software testing is the responsibility of the QA staff; do not add test modules to the project code.** Do not write or add test or self-check files such as `.test.ts`, `.spec.ts`, `scripts/check.ts`, or `check*.ts`; judge by actual purpose, whatever the file is named and wherever it is placed.
- Do not bypass this restriction through renaming, temporary test files, mocks/fixtures, test-only exports, or wrappers. Do not embed test assertions, self-check scripts, or DevTools self-check code in business source code or comments.
- Do not add test frameworks, test-only dependencies, test or self-check commands in package scripts, or automated CI test entry points. Do not implicitly bind checks, dependency installation, or environment preparation to development, build, or other commands.
- During development, you may explicitly run the existing `typecheck`, builds, and necessary manual verification for the current task, but do not add or keep test code because of it. Report verification results truthfully, and do not treat a successful compile as a passing functional test.
- **Runtime business validation must be kept.** Input validation, permission and path boundaries, file conflict protection, update checks, installation environment detection, and product debugging features are not test modules; do not delete them just because their names contain `check`, `assert`, or `debug`.
