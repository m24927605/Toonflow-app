# Tool Plugins

`packages/toolScaffold` provides the build entry, shared types, and the browser loader; `packages/tools/<name>` holds each tool package. Server logic and optional Vue components are bundled together into a single `.tool.js`, and installation, upgrades, and uninstallation all operate on this file.

Each tool package contains:

- `build.ts`: calls `createToolConfig(metadata, import.meta.url)` to declare the name, description, the package prompt `prompt`, and plain-JSON form-create configuration rules.
- An optional `readme.md`: read automatically at build time and embedded as `readme` in the first-line metadata, with no configuration in `build.ts`; it is an empty string when missing, up to 200000 characters.
- `src/index.ts`: default-exports a `ToolPlugin` implementing `validateConfig` and `createTools`.
- Optional Vue components: declare a mapping from tool name to component entry with `components: { askUser: "src/questionCard.vue" }`; one tool package can provide several components.
- `package.json` and `tsconfig.json`: declare the package's own dependencies and its build and typecheck commands. The builder reads the tool subpackage's `package.json.version` automatically and embeds it in the metadata. The version must be a non-empty string (at most 100 characters) and is not repeated in `build.ts`; change this version when releasing an update.

Running `bun run build` in the tool package directory only outputs `build/tools/<name>.tool.js`. During development, run `bun run dev:plugins` from the root, or build the tool with `NODE_ENV=dev`, to copy and sync it into `data/tools/`. Pi tool constructors are injected by the host through `context.sdk`; `zod` is shared by the Server, and other runtime dependencies are bundled with the plugin. A single-package build keeps the existing outputs of other tools.

`import { z } from "zod"` needs no changes: at build time `zod` becomes the external module `toonflow:tool-zod`, and the Server provides the full Zod 4 exports through a Bun virtual module before loading tools. Only the exact `zod` import is shared; subpaths are still bundled with the tool. When releasing these new outputs, update the Server at the same time; older tools that bundle their own Zod still load.

Running `bun run build:tools` from the repository root clears `build/tools` and builds all tools without touching `data/tools`; `bun run dev:plugins` syncs development outputs to `data/tools`. In Settings → Plugins, install `.tool.js` files, enable or disable them, uninstall them, or edit their configuration. Configuration is written to `toolConfigs` in `data/settings.json` and takes effect the next time a message is sent. Builds ship the default tools; after first-launch initialization, tools the user has uninstalled are not restored by an ordinary restart.

The first line of the file, `/*! toonflowTool:<JSON> */`, contains the `ToolMetadata`, where `version` is the tool version; it travels with the single `.tool.js` file when installed and shared. The server can read this data without executing the plugin. Older tools without a version still load; the list returns an empty string for an unknown version and never infers or fabricates a version number.

`configRules` uses the `Rule[]` of `@form-create/element-ui` directly, the same format as node configuration; `type`, `field`, `title`, `value`, `props`, `options`, `validate`, and so on follow the library's native rules. `field` maps to the configuration property and `value` is the default value. Rules are written to the metadata as JSON, at most 100 entries, and must not contain functions or other non-JSON values. The frontend uses a shared configuration dialog rendered with `<form-create>` and isolates form edits with `copyRules`. Plugins must validate configuration in `validateConfig` and must not rely only on frontend form constraints.

When `components` is configured, the builder compiles the Vue components with Vite. The second line, `/*! toonflowToolClient:<JSON> */`, stores the standalone UMD code and CSS, while the metadata stores only the tool names that have components. Components must explicitly import the UI components and styles they use and must not rely on the web app's auto-imports; Vue, Element Plus, Axios, and form-create reuse the host instances from `toonflowToolHost`. Other client dependencies are bundled with the component, and no resource files are generated outside the install package.

`/api/tools/renderers` lists only enabled component mappings and their content-versioned URLs, and `/api/tools/client` serves only the corresponding browser code and styles; neither executes nor exposes the server entry, configuration, or secrets. The web app uses `loadToolComponent(tool.name)` from `@toonflow/tools-scaffold/client` and always passes `{ tool: ToolCall, directory?: string }` to the component. Without a component, a plain tool message is shown; if loading fails, the user is told to stop and retry. Historical messages may only have `args/result`, so components must not assume live interaction data exists. `askUser`'s answering, skipping, and history display are all maintained by the package's own `src/questionCard.vue`; the web app does not import this component.

`createTools(context)` returns an array of Pi tool definitions; one plugin can provide several tools. The host passes in the current workspace `cwd`, the validated configuration `config` that belongs only to this tool, the unified file capability `files`, and the Pi SDK tool constructors. Application-wide settings and other tools' configuration are not passed in; any keys a tool needs are entered through its own configuration items. The workspace file plugin restricts paths through host methods; read-only mode registers only `read` and `ls`.

`context.files` provides `readFile`, `access`, `stat`, `readdir`, `detectImageMimeType`, `writeFile`, `mkdir`, `rename`, `remove`, and `copyFile`, all wired into the host's unified file layer. When a read method's second argument is `readOnly=true`, reading the global skills directory is also allowed; writes are always restricted to the current workspace. `writeFile(path, content, exclusive?)` saves atomically, and `exclusive=true` forbids overwriting; `mkdir(path, recursive?)` and `remove(path, recursive?)` are non-recursive by default; `rename` refuses to overwrite an existing target; `copyFile(path, target, exclusive?)` allows overwriting by default. The old `resolvePath` and `writeFile` entries remain; new tools use `files` to avoid importing file APIs directly or bundling the file layer implementation into the plugin. Older tools that call system APIs directly need their source updated and rebuilt.

`context.skills` provides unified skill scanning, reading, creation, and modification, reusing the host's SDK scanning and file persistence. `skillOperator` uses it to operate on the workspace `skill/` and the global `data/skills/` without bundling the Pi SDK into the tool. Reading, creating, and modifying are enabled by default and can each be turned off in the tool configuration; directory queries are always kept, and the write scope for ordinary workspace files is not widened by this.

`await context.ffmpeg(signal?)` returns a native `@renmu/fluent-ffmpeg` factory bound to `context.cwd`, available to both global tools and team-private tools; tools do not need to bundle the execution library. The factory's constructor arguments, chained methods, events, streams, `.run()`, `.save()`, `.pipe()`, `.clone()`, and `ffprobe` callbacks all follow the native API, and JSON plans are no longer recorded.

```ts
const ffmpeg = await context.ffmpeg(signal);
await new Promise<void>((resolve, reject) => {
  ffmpeg("assets/first.mp4")
    .input("assets/second.mp4")
    .complexFilter("[0:v][1:v]hstack=inputs=2[video]")
    .outputOptions("-map [video]")
    .videoCodec("libx264")
    .on("error", reject)
    .on("end", () => resolve())
    .save("assets/sideBySide.mp4");
});

ffmpeg.ffprobe("assets/first.mp4", (error, data) => {
  // Handle errors and media info with the native callback.
});
```

Explicit file paths can be workspace-relative paths or absolute paths inside the workspace. Prototype checks cover inputs, outputs and their aliases, screenshot directories, preset files, and cloned instances, and also check symbolic links and the existing parent directories of paths to be created. Native input and output streams are passed through as is. Indirect file access in FFmpeg arguments, filters, and media lists is not parsed separately. **These capabilities are for trusted code only and are not a file system sandbox**; they also do not guard against races where another process replaces a directory after the check.

Output overwriting, timeouts, events, and error handling follow the native library; callers are responsible for protecting source material by using new file names. `signal` only cancels the factory preparation stage; for a running command, the caller listens for cancellation and calls `command.kill("SIGKILL")`, also handling cancellation before start and listener cleanup. The entry checks FFmpeg/FFprobe on demand; when they are missing it still notifies the frontend to download them and throws `FfmpegRequiredError`. It does not install or retry automatically.

Tools no longer use `convert`, configuration callbacks, or JSON plans. `FfmpegFactory`, `FfmpegCommand`, and `FfprobeData` are exported from `@toonflow/ffmpeg/types` and `@toonflow/tools-scaffold/runtime`, reusing the native types directly. Browser nodes use the corresponding file-based chained API through `await useNode().ffmpeg(signal?)`, which is handed to the same host over an HTTP event stream; see `packages/nodeScaffold/readme.md` for the exact boundaries.

A tool package's static prompt is declared in `build.ts` with `createToolConfig({ ..., prompt: "Tool usage rules", configRules: [...] }, import.meta.url)`. `prompt` is an optional string of up to 20000 characters and supports multiline text; it is bundled with the metadata, and older plugins that do not declare it are treated as an empty string.

Tool definitions returned by `src/index.ts` keep `promptSnippet` as a short description of purpose; `promptGuidelines` holds dynamic rules generated from `context.config` and the runtime context, such as read-only mode or the current canvas ID. When extending SDK tools, append to the existing `promptGuidelines` instead of overwriting their rules.

The host merges the package-level `prompt` with the runtime `promptGuidelines`. The Agent only aggregates the summaries and rules of the tools actually loaded in the current turn and deduplicates identical text; when one tool package provides several tools, the package-level prompt appears only once. When a tool is disabled or returns an empty array because context is missing, its rules do not enter the system prompt. Adding a tool does not require changing `apps/server/src/agent/runtime/prompt.ts`.

Existing plugins:

- `skillOperator`: aggregates skill directory listing and reading/writing through `action: list/read/create/update`, operating on content and resources by `name`, `scope`, and the skill-relative `path`. By default, a workspace skill with the same name takes priority; new skills go to the workspace by default. `SKILL.md` name and description are validated; creation never overwrites, and updates only target existing files. Once enabled, this tool queries the directory on demand, and `/skill:<name>` invocation is kept.
- `askUser`: the question tool. It sends one or more questions at once through `context.question.ask` and continues after the user answers or explicitly skips. For a simple question pass `{ title, question, options? }`, which returns `{ answer }`; for multiple questions pass `{ title, question, fields }`, which the frontend renders with `@form-create/element-ui` and returns `{ answer, values }`. `fields` has at most 12 entries, one question each, containing a unique `field`, `title`, and `type`; answers may be left empty by default, and `required` and `placeholder` can be set. Supported types are `input`, `textarea`, `radio`, `checkbox`, `select`, `inputNumber`, and `switch`; choice fields must provide `options`. Dynamic forms and top-level `options` are not used together. Clicking "Skip" returns `{ answer: "用户跳过了本次提问", skipped: true }` ("The user skipped this question"), does not require filling required fields, and does not stop the Agent; stopping or disconnecting the conversation still cancels the wait. Questions, answers, and skip results are saved in the Pi tool call history.
- `canvas`: the canvas operation tool, which controls the active canvas bound to the current turn through the optional `context.canvas`. Read tools are the overview `getCanvas`, filtered and paginated `findCanvasNodes`, projected/segmented reads by ID `getCanvasNodes`, local connections `getCanvasEdges`, and the target node function query `getNodeTools`. Each read returns at most 64 KiB; continue with `hasMore/nextCursor`, and keep reading large node values along `path` with text or object/array offsets. `context.canvas` only needs the canvas ID and the call entry; the full function list is not injected. Mutation tools are `addNode`, `deleteNodes`, `moveNodes`, `renameNodes`, `connectNodes`, `deleteEdges`, `selectNodes`, `fitCanvas`, and `nodeTools`, the unified execution entry for node-registered functions; `deleteNodes`/`moveNodes`/`renameNodes`/`connectNodes`/`deleteEdges` all accept multiple targets for batch operations. Parameter rules are shared through the Zod schemas in `@toonflow/tool-canvas/runtime`. These tools are not provided when there is no active canvas; an empty canvas can still add nodes and then query and call the new nodes' functions. Execution goes through the Agent stream and callback endpoint; changes are made by the current Vue Flow instance and reuse the canvas save logic. Reads do not trigger saves, and the canvas is not controlled by editing JSON directly.
- `workspace`: workspace read, write, edit, and directory listing, with an optional read-only mode.
- `webSearch`: uses keyless DuckDuckGo by default and can be configured to switch to DeepSeek or Tavily with the corresponding key; the result count and timeout are configurable.
- `webFetch`: reads web pages with Bun's native fetch, with configurable timeout and body length; at most 5 redirects and a 2 MiB response body. It does not pre-check whether DNS resolves to public addresses and is compatible with Fake-IP; network isolation is the deployment environment's responsibility.

Tool plugins are trusted server-side code. Once imported they have the server process's permissions and **are not a sandbox**. Methods such as `context.resolvePath` constrain the behavior of the existing workspace tools but cannot stop third-party plugins from calling system APIs themselves. Only install tool files from trusted sources.
